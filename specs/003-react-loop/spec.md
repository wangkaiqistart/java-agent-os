# 功能规格：ReAct 循环（Agent 大脑）

**功能分支**：`003-react-loop`

**创建日期**：2026-10-19

**状态**：草稿

**输入**：根据 US-1“对接 LLM（Provider 抽象）”与 US-2“ReAct 循环（Agent 大脑）”的依赖表编写。US-2 依赖已完成的 Provider 能力。

## Clarifications

### Session 2026-10-19

- Q: Tool 执行失败时，ReAct 循环应如何继续处理？ → A: 将结构化失败结果回填给模型，由模型决定下一步；同一调用标识不得自动重试。
- Q: ReAct 循环的最大迭代次数应按什么单位计数？ → A: 每次 Provider 响应计为一次迭代，第一次调用为第 1 次；达到上限后不再调用 Provider 或执行 Tool。
- Q: 当会话历史超过允许发送给 Provider 的上下文范围时，运行时应保留哪些内容？ → A: 始终保留系统指令和当前请求，优先保留最新消息，丢弃最早的非系统历史，并记录发生了截断；US-2 不自动总结历史。
- Q: 同一个模型响应包含多个 Tool 调用时，ReAct 循环应如何安排它们的执行？ → A: 按模型返回顺序逐个串行执行，全部完成后再进入下一轮。
- Q: US-2 的会话上下文在进程重启后应如何处理？ → A: US-2 需要持久化会话上下文，并支持通过稳定会话身份跨重启恢复。

## 用户场景与测试

### 用户故事 1：让 Agent 生成最终响应（优先级：P1）

作为 Agent 使用者，我希望发送一条任务消息后得到最终响应，从而完成一次不需要工具的对话。

**优先级理由**：这是 ReAct 循环向用户提供价值的最小闭环，也是后续工具调用和记忆能力的基础。

**独立测试**：使用一个能够返回普通文本响应的 Provider，发送一条不需要工具的消息，验证消息被纳入当前会话并返回最终响应，且循环在一次模型响应后结束。

**验收场景**：

1. **假设**当前会话和 Agent 配置有效，**当**用户发送一条不需要 Tool 的消息时，**那么**运行时调用已指定的 Provider，并返回模型的最终文本响应。
2. **假设**模型返回最终响应，**当**本轮处理完成时，**那么**用户消息和最终响应按顺序保存在当前会话上下文中。
3. **假设**同一个会话连续收到多条消息，**当**处理下一条消息时，**那么**本轮能够看到该会话允许使用的历史上下文，并且不会混入其他会话的消息。
4. **假设**会话已有稳定身份且上下文已保存，**当**运行时重启后再次收到该会话的消息时，**那么**运行时恢复该会话允许使用的历史上下文，并继续处理本轮消息。

### 用户故事 2：根据模型决定执行 Tool 并继续推理（优先级：P1）

作为 Agent 使用者，我希望 Agent 能根据模型决定调用已授权的 Tool，读取执行结果后继续推理，直到得到最终响应。

**优先级理由**：Tool 调用是 ReAct 中“行动”和“观察”的核心，没有这一环节 Agent 只能生成文本，无法完成外部操作。

**独立测试**：准备一个返回一次 Tool 调用、随后根据 Tool 结果返回最终文本的 Provider，配置一个可用 Tool，验证调用顺序、结果回填和最终响应。

**验收场景**：

1. **假设**模型响应包含一个已授权 Tool 调用，**当**循环处理该响应时，**那么**运行时按调用名称和参数执行一次该 Tool，并将结果作为下一轮上下文的一部分提交给 Provider。
2. **假设**Tool 执行成功并返回结果，**当**Provider 根据结果生成下一轮响应时，**那么**运行时继续循环，直到响应不再要求 Tool 或达到终止条件。
3. **假设**模型响应包含多个 Tool 调用，**当**当前执行策略允许这些调用时，**那么**运行时按模型返回顺序逐个串行执行，每个调用都有独立的结果和审计信息，全部结果收集后再请求下一轮 Provider。
4. **假设**Provider 能够提供 Tool schema，**当**运行时向模型发送可用 Tool 列表时，**那么**只提供当前 Agent 被授权的 Tool，并且模型客户端不得自行执行 Tool。

### 用户故事 3：在受控边界内结束并记录循环（优先级：P1）

作为运维人员，我希望循环在错误、超时或达到最大轮数时可控结束，并能查看每轮模型和 Tool 活动，从而诊断 Agent 行为。

**优先级理由**：没有终止和审计边界，Agent 可能无限循环、重复执行操作或在失败后产生不可解释的结果。

**独立测试**：分别模拟 Provider 失败、Tool 失败和持续要求 Tool 的响应，验证每种情况都能在规定条件下结束、返回明确结果并留下可审计记录。

**验收场景**：

1. **假设**循环连续收到要求继续调用 Tool 的响应，**当**完成配置上限次数的 Provider 响应后，**那么**循环停止执行后续 Provider 和 Tool 动作，返回可识别的达到上限结果，并记录停止原因。
2. **假设**Provider 调用失败，**当**循环无法获取下一轮模型响应时，**那么**循环结束并返回包含失败类别的错误，不得继续执行上一次响应中的未执行 Tool。
3. **假设**Tool 执行失败或超时，**当**循环处理该失败结果时，**那么**运行时将结构化失败结果回填给模型，由模型决定下一步；同一调用标识不得自动重试。
4. **假设**循环完成、失败或达到上限，**当**处理结束时，**那么**每次模型调用、Tool 决策、Tool 执行结果和终止原因都能关联到当前会话和本次处理。

### 边界情况

- Agent 配置不存在或未通过校验：在调用 Provider 或 Tool 前返回清晰的配置错误。
- 模型请求未知或未授权的 Tool：拒绝该调用并回填可识别的 Tool 错误，不得执行未知 Tool。
- Tool 参数缺失、格式错误或超出策略范围：拒绝执行并记录校验结果。
- Tool 执行失败或超时：将结构化失败结果回填给模型，由模型决定下一步；同一调用标识不得自动重试。
- 模型返回空响应或无法识别的响应：结束本轮并返回明确的响应格式错误，不得凭空执行 Tool。
- 当前会话历史超过配置上限：始终保留系统指令和当前请求，优先保留最新消息，丢弃最早的非系统历史，并记录截断原因；US-2 不自动总结历史。
- 用户在循环执行期间重复提交同一消息：每次提交都拥有独立的处理标识，不得无依据合并两次处理。
- 运行时重启后无法找到指定会话：返回可识别的会话恢复错误，不得静默加载其他会话。
- 循环达到最大次数时仍没有最终文本：返回可识别的未完成结果，不能伪装成正常完成。

## 需求

### 功能需求

- **FR-001**：运行时必须提供一个由 AegisOS 控制的 ReAct 循环，接收用户消息和 Agent 配置并产生最终结果或明确失败结果。
- **FR-002**：每轮循环必须按照“组装上下文、调用 Provider、判断响应、必要时执行 Tool、回填结果”的顺序推进。
- **FR-003**：循环必须把用户消息、模型响应和 Tool 结果按发生顺序加入当前会话上下文，持久化上下文，并隔离不同会话的数据。
- **FR-004**：循环必须根据模型响应判断是否需要 Tool；没有 Tool 调用时必须返回最终响应，不得无故发起下一轮模型调用。
- **FR-005**：Tool 调用必须经过当前 Agent 的授权和策略边界；同一模型响应中的多个调用必须按模型返回顺序串行执行，每个调用最多执行一次。
- **FR-006**：循环必须将 Tool 执行结果以模型可理解的上下文回填给后续 Provider 调用，并保留调用名称、参数摘要和结果状态。
- **FR-007**：循环必须支持可配置的最大迭代次数；每次 Provider 响应计为一次迭代，第一次调用计为第 1 次，达到上限时必须停止后续 Provider 和 Tool 操作，并返回明确的终止状态。
- **FR-008**：Provider 或上下文组装失败时，循环必须返回稳定的错误类别并结束本次处理；Tool 失败时必须回填结构化失败结果，由模型决定下一步，同一调用标识不得自动重试。
- **FR-009**：循环不得依赖 Provider 客户端自动执行 Tool；Tool 的实际调度、结果回填和终止判断必须由 AegisOS 控制。
- **FR-010**：循环必须记录每次模型调用、Tool 决策、Tool 结果和终止原因，记录内容不得包含 API key、Token 或其他敏感凭证。
- **FR-011**：循环必须限制发送给 Provider 的会话历史和上下文范围；超出限制时必须保留系统指令和当前请求，优先保留最新消息，丢弃最早的非系统历史，并记录截断事件，US-2 不得自动总结历史。
- **FR-012**：本功能必须提供聚焦自动化测试，覆盖无 Tool 响应、单次 Tool 调用、多次循环、未知 Tool、失败重试禁止和最大迭代次数。
- **FR-013**：本功能必须通过项目规定的测试和打包验证，之后 Memory（US-3）与 Tool 体系（US-4）才能依赖它。
- **FR-014**：每个会话必须拥有稳定且唯一的会话身份；运行时必须保存该会话的上下文，并支持在进程重启后按会话身份恢复，不得将其他会话的数据用于恢复。

### 关键实体

- **循环处理**：一次从用户消息进入到最终响应、失败或达到上限的完整执行过程，拥有独立的处理标识。
- **会话上下文**：当前会话中按顺序累积的用户消息、模型响应、Tool 调用和 Tool 结果。
- **Tool 调用请求**：模型提出的 Tool 名称、参数和本轮调用标识，必须经过授权和参数校验。
- **循环事件**：模型调用、Tool 决策、Tool 执行、错误和终止等可审计事件。
- **终止结果**：最终文本、明确失败、达到最大迭代次数或其他受控结束状态。

## 成功标准

### 可度量结果

- **SC-001**：在聚焦自动化测试中，100% 的无 Tool 模型响应都在一次 Provider 响应后返回最终结果，且不产生额外 Tool 执行。
- **SC-002**：在聚焦自动化测试中，100% 的已授权 Tool 调用都按“模型决策 → Tool 执行 → 结果回填 → 后续响应”的顺序完成，未授权 Tool 的实际执行次数为零。
- **SC-003**：持续要求 Tool 的测试场景中，100% 的循环都在配置的最大迭代次数内结束，并返回可识别的终止状态。
- **SC-004**：验证套件中的每次循环处理都能关联到完整事件链；Provider 失败、Tool 失败和达到上限时均能识别终止原因。
- **SC-005**：循环能力通过聚焦测试和项目宪法要求的完整测试/打包验证，并且不把 Memory 后端、完整 Tool 目录或 Web Service 作为本功能的前置实现。
- **SC-006**：在跨重启恢复测试中，100% 的有效会话身份都能恢复其允许使用的历史上下文；未知会话身份不会恢复或泄漏其他会话数据。

## 范围边界

本功能包含 ReAct 主循环、会话上下文累积与持久化恢复、Provider 调用编排、Tool 决策与受控调度、最大迭代次数、错误处理和循环事件记录。

本功能不包含 Provider 连接和显式 Provider 注册（US-1）、长期 Memory 后端和统一 Memory 扩展（US-3）、完整 Plugin/MCP Tool 生态和完整 Sandbox 能力（US-4）、Web Service 端点（US-5）、Tool 并行执行、上下文自动压缩或 Agent 间委托。

## 假设

- US-1 已提供可按名称选择的 Provider，并能返回最终文本或 Tool 调用请求。
- Agent 已有一份可校验的配置，其中包含可用 Tool、上下文限制和最大迭代次数；最大迭代次数默认值为 10。
- 每个会话都有稳定且唯一的会话身份；恢复会话时调用方能够提供该身份，新会话由运行时生成并返回身份。
- Tool 执行由 AegisOS 的受控执行边界负责；本功能只消费该边界提供的调用结果，不定义完整的 Tool 实现集合。
- 初始循环以同步处理为主；流式输出、并行 Tool 和跨节点调度属于扩展能力。
- 事件记录遵循项目安全约定，敏感凭证永不写入响应、日志或审计数据。

## 依赖

- 依赖 US-1 的 Provider 抽象和显式 Provider 选择。
- 依赖项目统一的会话持久化和审计记录能力；长期 Memory 由 US-3 补充。
- Tool 授权、参数校验和执行结果必须与项目宪法规定的 Sandbox 边界兼容。
- 项目宪法约束 ReAct 归属、Tool 不得自动执行、用户故事测试和完整构建验证。
