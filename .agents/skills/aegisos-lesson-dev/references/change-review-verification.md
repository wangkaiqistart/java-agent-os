# 变更、Review 与验证说明契约

实现收尾或单独整理功能交付说明时读取。目标是让未参与开发的接手者能按文件入口审查代码、复跑验收并判断证据边界。

## 产物定位与历史

使用活动 feature，不从最大的目录编号猜测当前功能。优先更新已有同类指南；新指南默认 `docs/engineering/<feature>-changes-review-verification.md`，在 README 文档导航或已有 quickstart 链接。执行证据保存在该 feature 的 `validation.md`；默认不修改其他功能的任务和验证历史。

开始前记录当前范围、基线（commit/分支或修复前快照）及已有未提交改动。报告区分本次变更与既存问题，不将全工作区所有改动都算成本次修复；代码未提交时明确说明。

## 说明正文的必需内容

按下列顺序写，简单变更可简写，以下信息仍须齐全：

### 1. 变更范围与阅读地图

写清哪个用户场景、原行为、现在的行为；列影响模块/关键真实文件、生产入口/装配与推荐阅读顺序。必要时补充调用链、状态机、事务/schema/配置变化与兼容影响。源码和已批准规格优先于历史设计；计划中的能力另行标识。

### 2. 重点 Review

按真实风险选条目，不机械输出整份通用检查清单。对每个条目填写：

| 字段 | 内容 |
| --- | --- |
| 审查位置 | 文件/方法及必要的调用者、装配位置 |
| 必须成立的行为 | 路由、次数、顺序、身份、提交、资源释放等可判断的不变量 |
| 触发与反例 | 边界值、故障注入、重复/并发或非法输入 |
| 零副作用 | 拒绝后哪些模型/工具/持久化动作必须为零；如不适用说明原因 |
| 回归与证据 | 测试类/场景、实际断言、结果位置；区分只读推断与执行复现 |

沿跨模块生产调用链审查；数据写入/外呼之前的检查不能靠后置校验补救。锁、恢复、审计和安全缺陷应核对故障路径与关闭/重启后的状态，不能只验证 happy path。若实际执行独立 review，记录其范围、基线、问题/关闭依据及报告链接；未执行则标未执行。

课程流程中的六类边界逐项按本节范围检查：审计记录与实际调用是否配对；凭据是否仅受控注入；明文敏感内容是否进入库/日志/响应；异步或线程模型是否破坏上下文和资源生命周期；是否意外启用 Spring AI 自动 Tool 执行；YAML 配置与显式模型路由是否确实由生产装配采用。没有涉及的条目记“不适用”及依据。

发现缺陷时追加修复任务，按“回归RED → 最小实现 → GREEN → 相关门禁 → 复审”收敛。已有任务不重新编号，旧 FAIL 与新 PASS 分别记录；不要把未修复候选标成误报来清零。

### 3. 如何验证

提供接手者可复制的真实命令，说明仓库/环境、Java/Maven或其他依赖版本、配置/平台要求，以及预期断言。按需求组合：

- 聚焦回归与契约/生产装配集成验证；多模块过滤允许上游无匹配时，另核对每个目标类确实发现且执行。
- 项目约定的全量测试、打包、静态与安全门禁；串行保存各自报告，避免后续clean覆盖先前证据。
- 数据/schema变化的临时库迁移、旧数据双向核对、关闭重开与恢复；个人/生产库按授权另行处理。
- 独立真实验收的前置条件、明确开关、run-id/预算、业务语义与审计核验；方法和授权分开，不因指南存在便自动执行。

只列真实存在的命令/脚本。私有忽略目录内工具可以作为历史证据，不能是接手者唯一的复跑入口。平台差异要分别说明：拒绝路径验证与支持平台的正向验证不能相互替代。

### 4. 实际结果与可追溯证据

每组记录以下字段；未执行填 NOT_RUN/原因，不编造默认值：

| 时间/代码基线/环境 | 命令及退出码 | 本轮测试发现/失败/错误/跳过 | 行为或业务断言 | 证据位置 | PASS / FAIL / NOT_RUN |
| --- | --- | --- | --- | --- | --- |

结合开始时间、源码基线及本轮报告判断新鲜性。多模块中途失败，未执行模块的旧 XML 不计入通过；没有目标、跳过、缺凭据、缺平台或仅有准备文件都不能判 PASS。业务验收还须核对数据归属、事实/状态、计数及持久化回读，不能只看HTTP200、非空回答或JSON自报PASS。

对可诊断的失败先保存证据，修复或确认原因后运行相关验证；不通过盲目重跑抹去失败。凭据不入库、不写报告，敏感原文/个人库保留在受控范围。扫描误报应提供依据，优先消除无意义的证据格式歧义，不为通过而降低规则。

纯文档/skill变更不默认重复运行Maven：核对相关Java/POM与最近已验证基线一致，执行受影响的结构/引用检查，说明引用哪次执行记录；新增功能/修复则按影响范围取得新证据。

### 5. 完成状态与交付边界

给出完成/尚缺条件及原因，区分代码实现、静态review、执行测试、真实验收、Git交付与生产部署。列平台限制、未纳入能力和剩余风险；任务状态与验证证据一致。

代码或测试失败未闭合、必要验收NOT_RUN时，不宣布整个功能完成。若用户仅要求文档或收尾总结，交付该范围并说明原功能的验证状态，不借机实施下一US或重新发起真实外呼。

## 本项目实例

使用 `docs/engineering/us2-changes-review-verification.md` 作为完整实例。US2的固定测试数量、历史平台结论、真实天气预算及已通过run-id属于该功能，不能复制成其他课程或后续执行的默认事实。
