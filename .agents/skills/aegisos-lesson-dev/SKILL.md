# AegisOS 课程开发与交付复核

以真实课件、当前规格和源码为依据复用现有 Spec-Kit。每次实现收尾应让接手者知道：**代码改了什么、重点审查哪里、如何复跑验证、哪些结果已有证据**。产物尽量使用中文，运行配置使用 YAML，关键代码用中文解释设计理由。

## 输入与模式

- 输入为课程章节号、US 编号、feature 路径或明确的课件。先检查已有产物，避免重复创建同一个功能。
- **开发模式**：用户要求按课实现，执行下述课程流程；仅推进本次已授权的阶段。
- **收尾模式**：用户要求总结变更、说明重点 review、给出验证方法或整理交付说明，直接定位现有 feature 并执行第7步；不因此重新 specify、修改 Java 或发起真实模型调用。
- 缺少会改变范围的课件/章节信息时，只询问缺项，同时进行不依赖答案的只读核验。

## 课程流程

### 0. 判定课型

沿用课程流程的初始索引：代码课为16～20、22、24～26、29、30节；评审课为21、23节；串联课为27、28节；Demo为31节。最终以实际课件判定，编号不能代替正文；发现课程版本不同则记录差异再调整映射。

| 课型 | 处理方式 |
| --- | --- |
| 代码课 | 交付对应模块，走现有 Spec-Kit 流程 |
| 评审课 | 输出评审素材/后续 specify 输入，不把“评审完成”冒充代码实现 |
| 串联课 | 复用已完成模块，补集成验收；不无依据新建重复 feature |
| Demo | 按当前配置规范装配 Agent 和验收；课件未要求的模块开发不顺带进行 |

### 1. 实现前核查

定位 `docs/class/` 或仓内实际课件路径；同时读 `AGENT.md`、宪法、活动 feature 和 `docs/TechnicalSolution.md` 的对应章节。用 `rg` 与源码确认模块、类型、入口、表和已有测试，输出简短映射：`课程条目 → 技术方案章节 → 现有实现/缺口 → feature/US`。缺资料和冲突明确记录，不编造课件内容或完成状态。

版本/模块数从当前 POM 与已批准规格取值；不为课堂示例自动升级依赖。课件与已批准设计的差异交给 clarify，不能静默选边。

### 2～4. specify → clarify → plan

依次使用项目已有 `speckit-specify`、`speckit-clarify`、`speckit-plan`。已完成且仍适用的阶段直接复用；保留旧 feature 与验证历史。仅有文字自述而没有源码/交付物不能视作已实现。

### 5. tasks 与范围确认

使用 `speckit-tasks`，对照课件、本节交付物和已批准 plan 输出差异。首次进入 implement 前，若当前范围尚未获得用户确认，先展示可审查的任务与差异并等待；已有确认或用户明确授权本次修复时沿用授权，不重复索要确认。收尾模式不触发这一实施入口确认。

### 6. analyze 与 implement

按现有 `speckit-analyze` 核对阻断问题，再用 `speckit-implement` 执行已确认任务。修复缺陷时先补回归并确认行为失败，再实现和验证；发现新问题追加任务，原编号、勾选和 FAIL/PASS 记录保留。跨模块变更按真实契约接线，不能仅有 mock 证明生产链路可运行。

### 7. 变更总结 → 重点 Review → 验证与交付说明

**这是实现收尾与收尾模式均需完成的环节。** 先读 [交付说明契约](references/change-review-verification.md)，生成或更新 `docs/engineering/<feature>-changes-review-verification.md`；已有对应指南时更新原文件并保留历史，不另建重复报告。

1. **变更总结**：写明原行为/新行为、影响模块与关键入口、调用/状态或持久化变化，给出真实文件链接和建议阅读顺序；覆盖本次批准范围，而不只列文件数。
2. **重点 Review**：给出按风险排序的具体路径、不变量、触发反例、零副作用与回归入口。需要实际代码复审时使用 `reviewing-code`，按其当前工作流完成独立核验；接手者阅读指南不能冒充已执行独立复审。旧问题、已关闭问题、剩余问题分别标明。
3. **验证**：提供可复跑命令、环境/前置条件与每条命令验证的行为，分别记录静态审查、已执行测试、构建、安全检查、真实验收和未执行范围。发现失败先诊断，修复后重验受影响范围，保留首次失败和后续结果。
4. **证据**：本轮命令与退出码、测试发现/失败/错误/跳过数、XML/审计重开及报告位置写入活动 feature 的 `validation.md`；指南引用这些证据。没有本轮执行证据的命令只标“操作方法/待执行”，不得写 PASS。
5. **完成判定**：构建、生产装配/隔离测试、存在性/字段/语义断言与约定门禁齐备，相关 review 问题闭合后才标完成。校验文档链接、任务状态和实际证据一致；在 README 或已有功能指南提供入口。

US2 的项目实例是 [变更、Review 与验证指南](../../../docs/engineering/us2-changes-review-verification.md)；只复用结构，不复制其固定测试数量或历史 PASS。

### 硬、软门禁与 DoD

- **硬门禁**：可确定的条件用脚本、测试和真实产物检查；构建或交付物缺失、约定测试失败、前序能力回归、安全门禁失败时不放行。`mvn clean verify` 包含哪些静态检查以当前 POM/profile 为准，不能凭命令名称声称运行了未配置的工具。
- **软门禁**：边界划分、课件与方案冲突、第三方 API 事实等判断写清依据；不能确定时记录 `disabled`/未启用的具体原因，提交当前必要决策给用户，不编造默认结论。
- **六项 DoD**：按本节范围核对构建与静态检查、harness/场景断言、交付物存在性、前序能力回归、六类边界审查、验收证明。六类边界是审计链、凭据与敏感信息、无明文泄露、异步/线程模型、Spring AI 自动工具执行、配置与模型路由；具体断言见交付说明契约。不适用项说明原因，不能机械补功能。
- 完成宣告要有实现者自检与复核证据；未做独立复审时明确说明，不把同一份实现者总结写成独立审查。存在未关闭的阻断问题时不能放行下一阶段。

## 执行与验证边界

- 静态 review、Maven、依赖安全、真实外呼是不同证据。`mvn clean verify` 不能代替真实课程场景验收；HTTP成功或回答非空不能代替业务事实、审计关联与重开核验。
- 同一工作区的 Maven/clean 门禁串行；聚焦目标零发现、跳过、过期 XML 和中途失败后其他模块残留的旧 XML 均不能算通过。测试数量从实际报告读取。
- 默认构建不启用 real-*；真实模型/外部工具、个人库迁移和部署依当前用户授权执行。运行失败不隐藏重跑；凭据不写入 YAML、参数、日志、报告或 Git。
- 平台不支持安全读取/锁属性时如实记录；macOS拒绝路径不能冒充Linux正文正向验收，不弱化已批准安全契约。没有新依赖也不能将旧扫描称作本次扫描。
- 本 skill 的实施/收尾不包含自动 commit/push；Git交付按用户单独指令执行。产物留在当前项目，保留既有未提交改动。

## 收尾报告

向用户提供：变更主旨、重点审查结论、实际验证结果与局限、交付说明/验证记录链接，以及提交/推送/部署状态。待修复问题或必要验收未通过时，报告具体缺口和当前已完成范围，不输出笼统的“全部完成”。
