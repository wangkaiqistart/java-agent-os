# AegisOS 工程初始化

将已有工程补成可编译、可启动、可检查的开发基线。先识别已经存在的能力，再补缺口；一次执行只覆盖用户指定的初始化范围。默认保留现有框架版本、模块划分和未提交修改，不重新下载脚手架覆盖项目。

## 输入与事实源

- 以用户指定目录为根；未指定时从当前目录向上定位根 POM，不假设终端已经位于 Git 根目录。
- 读取根目录 Agent 指南、`.specify/memory/constitution.md`、根/相关模块 POM、源码、应用配置、现有 CI 与忽略规则。按任务读取 `docs/TechnicalSolution.md` 与 `docs/AiProgrammingGuide.md` 的基础工程章节。
- 若存在 `.specify/feature.json`，解析活动 spec/plan/tasks，检查初始化是否已被现有任务覆盖。功能目录标识不等于当前 Git 分支；不要调用会覆盖 plan 的 setup 脚本。
- 默认从 [基础建设约定](references/baseline.md) 取实现边界；实施时再读 [验证清单](references/verification.md)。模板按需加载，不整包复制。

## 执行方式

### 1. 检查现状并明确增量

读取 `git status`、改动摘要、Java/Maven 版本及真实模块布局。输出一张“已有 / 缺失 / 本次处理”的简表，覆盖日志、监控、HTTP/API、代码规范、安全和验证入口。

当前 AegisOS 的宪法基线是九模块；源码/POM 是工程现状，文档中的十四模块或“暂无工程”不能直接当实现事实。遇到实质架构冲突时指出冲突，不借初始化修订宪法或扩模块。

若用户只要求检查或设计，到结论为止；若已要求执行初始化，继续完成已授权的本地改动与验证，无需再要求逐项确认。跨模块公共契约或用户可见端点变更须遵循仓库 Spec Kit 约定：优先使用已覆盖此范围的规格，缺失时先补独立基础工程规格，不混入 Provider 规格、不静默切换其活动元数据。仅要求编写 Skill 时不执行本流程。

### 2. 合并基础配置

按 [基础建设约定](references/baseline.md) 定点修改：

1. 根 POM 集中 Java、测试与质量插件版本；受影响模块仅增加所需依赖。core 不为日志/监控/API 引入 Web、Spring AI 或存储实现依赖。
2. 补齐请求关联、日志字段及敏感信息省略；区分诊断日志与必须持久化的业务审计。
3. 复用现有 Spring MVC Server，增加合理边界配置、最小健康检查；指标导出按用户范围启用，不默认暴露管理详情。
4. 在 web 定义基础错误响应与输入校验约定；只实现规格已批准的公共接口，不提前创建五大业务能力的端点。
5. 配置 Google Java Style 格式化、静态检查、秘密扫描和依赖扫描入口；明确哪些常规门禁默认运行、哪些依赖网络的安全门禁由 CI 单独执行。

交付一个仓库原生入口（已有脚本则复用），能分别运行 quality、secrets、dependencies；CLI 缺失时非零退出并提供安装提示，不静默跳过。CI 调用同一入口，避免本地与 CI 两套规则。工具版本锁定；执行前检查安全插件是否仍能消费当前漏洞数据格式。

参考 [Maven 合并模板](assets/maven-quality.fragment.xml) 和 [Boot 配置参考](assets/boot-baseline.fragment.yaml)。两者都是片段，不是完整 POM/应用配置。合并到现有同名节点，不重复导入插件、starter 或日志实现。若已有等价工具，保留并验证，避免叠加两套格式器或规则互相冲突。模板版本需重新验证兼容，不能因标注过 HTTP 200 就声称已经安全或通过构建。

项目已批准的 Boot/Provider 版本升级按对应 plan 执行，初始化本身不为了模板升级依赖。OpenAPI、JSON 日志等配置必须与实际 Boot 版本匹配，不把较新版本属性套到旧版。

首次启用格式门禁时，先查看现有源码范围。初始化授权包含让此次门禁通过所需的少量骨架格式整理；大规模既有业务代码重排须隔离处理，不借此覆盖用户改动。记录被整理文件，不设置临时 ratchet 或跳过旧文件来伪造全仓通过。

### 3. 验证后收口

先运行受影响行为的聚焦测试，再按 [验证清单](references/verification.md) 完成 Maven 与启动检查。新增 HTTP/日志/监控行为必须有实际测试；零测试发现不能作为通过。

本地开发遇到可修复的配置问题可以修复并重跑相关检查；凭证、依赖数据源或工具不可用时明确记录阻塞，不把跳过算通过。不要为跑通检查降低规则、禁用审计、启用底层隐藏重试或添加真实密钥。

依赖数据库首次更新须设置有限连接/读取超时；网络失败保留失败关闭并报告，不无限循环重试。历史漏洞、历史秘密和历史 tracked 构建物与本次新增问题区分，不自动扩大为清理历史。若测试会改写已 tracked 的构建物，执行前备份，完成打包演示后恢复原有字节，不覆盖原本未提交的修改。

使用 [报告模板](assets/initialization-report.md) 在根目录 `docs/engineering/initialization.md` 记录最终配置、修改文件、有效命令、结果及遗留项；若已有同用途报告，增量更新。重复执行保留已有决策，避免无关格式重排。报告中区分 PASS / FAIL / NOT_RUN / N/A，附本次证据而非预填成功。

## 交付边界

- 复用当前模块：boot 装配/监控配置，web 承载 Web 基础行为，core 只保留真正公共的稳定契约；根 POM/CI 管理质量门禁。不预设新增 common 模块。
- 不实现模型调用、ReAct、Memory、Tool、人工坐席、电话或业务 API。已有持久审计要求保留，不能用 Logback 替代。
- 不默认安装外部 Skill、连接真实 Provider、启动数据库/云服务、提交、推送或发布。用户在当次会话已明确授权的动作按授权执行。
- 探测与演示尽量使用临时目录、loopback、测试 Profile 和本地桩；启动进程后负责停止，不占用用户原服务。
- 最终说明完成内容、受影响文件、执行证据及尚未执行项。下一步才是业务 User Story；未通过基础门禁时不声称已具备业务能力。
